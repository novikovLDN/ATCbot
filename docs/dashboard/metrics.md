# Метрики дашборда — единый источник правды

Обновлено: 2026-09-14 (dashboard v4). Каждая цифра на дашборде считается одной функцией:

| Что | Где |
|---|---|
| Деньги | `database/revenue.py` |
| Подписчики, воронка, платежи, выдача, вовлечённость | `database/metrics.py` |
| Здоровье системы | `app/services/system_health.py`, `app/core/runtime_health.py` |
| Панель Remnawave | `app/services/panel_stats.py` |
| Роуты (тонкие, только чтение) | `app/api/dashboard/routes/metrics.py`, `panel.py` |
| Подсказки «?» в интерфейсе | `dashboard/src/lib/metricDefs.ts` — тот же текст, что здесь |

Роуты своего SQL не пишут. Меняется определение — правятся код, тест и этот файл вместе.
Тесты: чистые функции — `tests/services/test_revenue_definitions.py`, `test_dashboard_metrics.py`,
`test_dashboard_v4.py`; SQL на настоящем Postgres — `tests/db/test_dashboard_sql.py` (один набор
фикстур, каждое число проверено точно; в CI — шаг «Dashboard metric SQL on Postgres» гейта миграций,
локально — `DASHBOARD_TEST_DATABASE_URL=… pytest tests/db`).

## Общие правила

| Правило | Значение |
|---|---|
| Бизнес-сутки | **Europe/Moscow** (UTC+3, без перехода на летнее время). Окно «N дней» = N московских суток, сегодня — до текущей минуты. |
| Сравнение с прошлым периодом | **Такой же отрезок, сдвинутый на N суток назад**: `[since − N, now − N)`. «Сегодня» сравнивается со вчера до того же часа (`revenue.window`). Изменено в v4, см. «Изменения определений». |
| Дельта | `(текущее − прошлое) ÷ прошлое × 100`, одна цифра после запятой; при прошлом = 0 — «нет базы для сравнения» (`revenue.delta_pct`). |
| Параметры времени в SQL | naive UTC через `_to_db_utc` (конвенция репо). У конвенции две половины: asyncpg переводит naive-время в параметре `TIMESTAMPTZ` по **часовому поясу процесса бота**, а колонки `TIMESTAMP` сравниваются в **часовом поясе сессии Postgres**. На Railway оба UTC (в Dockerfile `TZ` не задан, Postgres по умолчанию UTC). На ноутбуке с другим поясом границы окон сдвигаются — тесты `tests/db` фиксируют оба пояса в UTC. |
| Единицы | Копейки (int) во всём API. Рубли — только в форматтере интерфейса (`fmtKop`). |
| Момент признания выручки | `pending_purchases.created_at` (старт оплаты, счёт живёт 15–30 мин). Пополнения в Telegram — `balance_transactions.created_at`. |
| Stars | По `price_kopecks` — рублёвой цене каталога, записанной в покупке; `payments.amount` — та же сумма в рублях (`successful_payment` переводит звёзды в рублёвую цену покупки). Показываются отдельно: курс звезды не утверждён. ⚠️ **Исторические строки** VPN-подписок за Stars, созданные до исправления (2026-09-14), хранят в `price_kopecks` и `payments.amount` **число звёзд** (×100 и ×1) — их рублями не считать; подарки за Stars всегда хранили рубли. Пакеты ГБ за Stars ботом не продаются. |
| Комиссии | Не учитываются: выручка — **до комиссий** провайдеров. |
| Чтение | Каждый SQL дашборда — в `READ ONLY` транзакции с `SET LOCAL statement_timeout` (`database/readonly.py`, по умолчанию 5 с, `DASHBOARD_STATEMENT_TIMEOUT_MS`). Метрика не может ничего записать и не держит соединение пула дольше таймаута. |
| Кеш | На сервере, в памяти процесса (`dashboard_cache`): здоровье системы 30 с, выдача 30 с, отчёты 60 с, вовлечённость и когорты 5 мин, панель 45 с. Одновременные запросы одного ключа ждут одну загрузку. |
| HTTP и БД | Проверки панели, Telegram и Redis не выполняются, пока открыто соединение с БД. |

## Где записаны деньги (проверено по коду оплаты)

| Поток | Таблица | Примечание |
|---|---|---|
| Внешние провайдеры (Platega, WATA, CryptoBot), оплата в Telegram подписок / подарков / пакетов | `pending_purchases` (`status='paid'`, `payment_provider`) | `finalize_purchase`; `payments` получает строку с `purchase_id` и `paid_at` |
| Магазин (Premium, Stars, Steam, Apple ID, Spotify) | `pending_purchases` | `mark_pending_purchase_paid` **не пишет провайдера** → «Без провайдера» |
| Пополнение баланса через провайдера | `pending_purchases` (`balance_topup`) | `price_kopecks` — сумма, которую заплатил пользователь, **включая наценку СБП** (`SBP_MARKUP_PERCENT`); она и считается выручкой, `payments.amount` — та же сумма. На баланс с 2026-09-14 зачисляется только запрошенная сумма (`credit_kopecks`, миграция 083); разница — не обязательство перед пользователем |
| Пополнение баланса внутри Telegram (карта / Stars) | **только** `balance_transactions` (`type='topup'`, `source IN ('telegram','telegram_stars')`) | `finalize_balance_topup` |
| Покупка с баланса, автопродление | `payments` + `balance_transactions` (`type='subscription_payment'`, у автопродления `source='auto_renew'`) | в `pending_purchases` не попадают |
| Неоплаченные счета | `pending_purchases` (`status='pending'`) | **Ничто не помечает их истёкшими по сроку**: `expire_old_pending_purchases` нигде не вызывается. Счёт закрывается как `expired`, только когда пользователь открывает новый (или сверка WATA). Брошенные корзины остаются `pending` навсегда — метрики ниже учитывают это явно. |

| ARPU | выручка VPN ÷ зарегистрированные на конец окна | `money_report → arpu_kopecks` | окно | |

| MRR | Σ по активным подпискам: цена последней прямой покупки ÷ дни периода × 30 | `mrr_snapshot()` | сейчас | подписки, купленные только с баланса, не видны. | Обязательства | Σ положительных `users.balance` + заявки на вывод `pending` | `liabilities()` | сейчас | |

## Платежи: здоровье (`metrics.payments_health`, роут `/metrics/payments-health`)

| Метрика | Формула | Источник | Период | Оговорки |
|---|---|---|---|---|
| Конверсия / успешность по провайдерам | как в «Деньгах» | `provider_performance(24 ч)`, `(7 д)` | 24 ч, 7 д | |
| **Не закрыты > 30 мин** | `status='pending'`, созданы от 30 мин до 24 ч назад, по провайдерам; рядом — сколько счетов открыто за сутки | `_STUCK_SQL` | 24 ч | почти всегда брошенные корзины; всплеск относительно числа счетов — повод проверить вебхуки |
| **Время до оплаты** | `payments.paid_at − pending_purchases.created_at` по `purchase_id`: медиана и 90-й перцентиль, всего и по провайдерам | `_TTP_SQL` (GROUPING SETS) | 7 д | только оплаты с `paid_at` (без магазина и покупок с баланса) |
| **Ошибки платежей** | `payment_errors` за 24 ч: по этапу × провайдеру, последняя; «деньги в Telegram» = этапы `telegram_*` | `_ERR_MATRIX_SQL`, `summarize_errors()` | 24 ч | этапы: `amount_mismatch`, `webhook_provider_mismatch`, `*_purchase_not_found`, `telegram_payment_rejected`, `telegram_gift_failed`, `telegram_traffic_pack_*`, `provisioning`, `renewal_sync`, `bypass_topup`, `platega_recurring_disabled`… |
| **Последняя оплата** | время последней оплаченной покупки провайдера (по `id`, `paid_at` если есть) и последнего пополнения в Telegram | `_LAST_PAID_SQL`, `_LAST_TOPUP_SQL` | всё время | запрос идёт по pkey назад и останавливается на первой строке |

| Статус раздела | критично: ≥ 10 ошибок за 24 ч; внимание: 1–9 ошибок, молчащий провайдер, успешность < 50 % при ≥ 20 закрытых счетах за 7 д | `payments_verdict()` | | |

| Проверка | Как | Оговорки |
|---|---|---|
| База | `DB_READY`, размер пула / занято (`get_size − get_idle_size`) / максимум, `SELECT 1` с таймаутом 3 с | соединение возвращается до HTTP-проверок |

**Ноды в статусе обзора (v5).** Выключенные в панели ноды (`isDisabled`) — не проблема и не «офлайн»:
`/panel/nodes` отдаёт их отдельно (`disabled`, `enabled = total − disabled`). Не в сети = `offline` + `connecting`.
Алерт `nodes_offline`: **внимание**, если не в сети меньше половины включённых нод (клиенты переключатся), **критично** —
половина и больше (`build_alerts`, тесты `tests/api/test_dashboard_metrics_api.py`).

**Расхождение БД ↔ панель.** У пользователя в панели две сущности (premium + bypass). Сравниваем
`ACTIVE` панели с «premium с доступом + bypass-сущности с UUID». Разница — сигнал для аудитов, не
точная метрика: bypass в LIMITED легитимен.

## Производительность

Дашборд живёт в одном процессе и на одном пуле с ботом. Замер на объёме, похожем на прод
(pgserver, PostgreSQL 16; 60 тыс. пользователей, 40 тыс. подписок, 400 тыс. счетов, 300 тыс.
платежей, 300 тыс. движений баланса, 250 тыс. заданий выдачи, 1 млн строк журнала рассылок,
600 тыс. отправок автоуведомлений), холодный вызов, без кеша:

| Функция | мс |
|---|---|
| `revenue.totals` 7 д / 30 д | 27 / 17 |
| `revenue.payers` 7 д | 67 |
| `revenue.provider_performance` 7 д | 9 |
| `revenue.money_report` 30 д (весь экран «Деньги») | 338 |
| `metrics.new_users` 7 д | 0,5 |
| `metrics.active_subscriptions` | 6 |
| `metrics.subscription_motion` 30 д | 171 |
| `metrics.trial_conversion` 30 д | 111 |
| `metrics.renewal_pipeline` | 25 |
| `metrics.payments_health` | 40 |
| `metrics.delivery_health` | 50 |
| `metrics.engagement` 7 д | 11 |
| `metrics.subscribers_report` 30 д | 417 (до v4: > 5 с, упирался в таймаут) |

EXPLAIN: `new_users` — индекс `idx_users_created_at`; зависшие счета — `idx_pending_purchases_status`;
последняя оплата — обратный проход по pkey, 0,01 мс; воронка продлений — `idx_subscriptions_active_expiry`;
ошибки за 24 ч — `idx_payment_errors_created_at`; автоуведомления — `idx_ans_key_sent` на каждый ключ.
Окна по `pending_purchases.created_at` читаются параллельным seq scan (индекса по `created_at` нет):
8,7 мс на 400 тыс. строк. **Новых индексов и миграций нет**: при таком объёме выигрыш не стоит
блокировки таблицы платежей при деплое (миграции выполняются в транзакции, `CONCURRENTLY` невозможен).
Если `pending_purchases` вырастет на порядок — первым кандидатом будет индекс по `created_at`.

## Изменения определений (v3 → v4)

| # | Метрика | Было | Стало | Почему |
|---|---|---|---|---|
| 1 | Прошлый период во всех дельтах | N полных прошлых суток против N−1 суток + части сегодняшних | тот же отрезок, сдвинутый на N суток | в 10:00 недельная выручка была на ~1/7 меньше «прошлой» просто из-за неполного дня |
| 2 | Успешность провайдера | брошенные счета (`pending` после срока) не учитывались | считаются неоплаченными; добавлена конверсия (оплачено ÷ открыто) | счета не закрываются по сроку, успешность была завышена (на фикстуре Platega: 75 % → 60 %) |
| 3 | Пробный → оплата за 7 / 30 дней | делилось на все пробники окна | только на пробники, которым уже 7 / 30 дней | вчерашний пробник считался «не оплатил за 7 дней» (на фикстуре: 40 % → 33,3 %) |
| 4 | Провайдер Telegram | `telegram` и `telegram_payment` — две строки в таблице провайдеров | одна | одно и то же, два написания |
| 5 | Воронка | коррелированный EXISTS | полу-соединения | не укладывалась в 5 с на реальном объёме; результат тот же (тест) |

## Что не добавлено и почему

| Метрика | Почему нет |
|---|---|
| Возвраты и чарджбэки (реальные числа) | Бот их не записывает: вебхуки Platega CHARGEBACKED и WATA Refund игнорируются. Плитка показывает ноль с пояснением; числа появятся без правки дашборда, когда платёжное ядро начнёт писать их в `payment_errors`. |
| Просмотр экрана тарифов в воронке | Событие не логируется, таблицы событий нет. Шаг показан как «нет данных». |
| Реальная сумма ближайших автосписаний | Воркер применяет персональную скидку в момент списания. Дашборд показывает цену по прейскуранту с пометкой «верхняя оценка». |
| Число напоминаний (а не пользователей) | В `subscriptions` хранится только последнее напоминание; журнала напоминаний нет. |
| Активные подписчики N дней назад (прирост как разница остатков) | Таблица подписок хранит только текущее состояние; прирост показан как поток: новые платящие − ушедшие. |
| Рекуррентные списания Platega в выручке и воронке продлений | Списания не пишутся ни в `pending_purchases`, ни в `payments` (таблица `platega_subscription_charges` не заполняется кодом). Показаны только статусы подписок Platega. |
| Несовпадения выдачи на старом пути (`verify_delivery`) | Этот путь пишет только в лог и алерт, не в `payment_errors`. Видны несовпадения из очереди выдачи. |
| Кнопка «повторить dead-задание» | Безопасного аудируемого эндпоинта нет; дашборд только читает. Показан SQL для ручного повтора. |
| Эндпоинты панели сверх используемых | Только то, что уже вызывает `remnawave_api.py` (контракт 3.4.3); онлайн — из `onlineStats`. |

## Решения владельца (2026-09-13)

1. Выручка признаётся в момент прихода денег: пополнение — при пополнении, покупки с баланса повторно не считаются.
2. Магазин, MTProto-прокси и игра — отдельные строки, не внутри выручки VPN. Вместе с VPN — оборот.
3. Бот для ссылок — `config.BOT_USERNAME` (переопределяется `BRAND_BOT_USERNAME`).
4. Бренд — «Atlas Secure»; логотип и акцент — через переменные окружения.
5. Курс Stars и комиссии провайдеров не утверждены: выручка «до комиссий», Stars отдельно с пометкой.
