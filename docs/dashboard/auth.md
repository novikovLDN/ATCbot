# Вход в дашборд (v3)

## Как войти

1. В боте отправь `/admin` → кнопка «Открыть дашборд». Ссылка содержит одноразовый токен и
   **живёт 15 минут** (раньше — 30 дней).
2. **Первый вход** (нет ни пароля, ни passkey): откроется форма «придумай логин и пароль».
   Токен из ссылки отправляется в теле `POST /auth/setup` и больше нигде не используется.
3. **Обычный вход**: логин + пароль или Face ID / Touch ID (passkey). Ссылка из `/admin` при
   этом только открывает страницу входа — сама по себе больше не пускает.
4. **Забыл пароль**: в боте «Сбросить пароль» (стирает пароль, passkey и все сессии) → снова
   `/admin` → форма установки пароля (в течение 15 минут).

Сессия — HttpOnly-cookie `atlas_admin_session` (Secure, SameSite=Lax, путь `/dashboard/`), 5 дней.

## Что изменилось по безопасности (recon P1-1, P1-2)

| Было | Стало |
|---|---|
| Magic-link JWT 30 дней принимался как `Authorization: Bearer` для всего API даже после установки пароля | Bearer принимается **только** пока нет ни пароля, ни passkey, и только если токен выпущен ≤ 15 мин назад (проверяется `iat`, поэтому старые 30-дневные ссылки мертвы сразу после деплоя) |
| `GET /auth/verify?token=` без авторизации отвечал, валиден ли токен, и отдавал его claims | эндпоинт удалён |
| WebSocket `/dashboard/ws?token=<jwt>` | только cookie + проверка `Origin` (защита от cross-site WebSocket hijacking) |
| Нет ограничения попыток | `/auth/login`: 5 неудач на логин или 10 на IP за 15 мин → блокировка 15 мин (429 + `Retry-After`), даже верный пароль не пройдёт до конца блокировки. `/auth/setup`: 5 неудач с IP. Passkey-проверка: 10 неудач с IP. Счётчики в Redis, без Redis — в памяти процесса |
| Нет CSRF-защиты | каждый POST/PUT/PATCH/DELETE под `/dashboard/api` проверяет `Origin` (или `Referer`) = `DASHBOARD_BASE_URL` / собственный хост; с cookie и без обоих заголовков → 403; `Sec-Fetch-Site: cross-site` → 403 |

IP клиента — последний адрес в `X-Forwarded-For` (его дописывает edge Railway; всё левее мог
подставить клиент).

Код: `app/api/dashboard/auth.py`, `deps.py`, `security.py`, `ws.py`. Тесты:
`tests/api/test_dashboard_auth.py`.

## Для curl / скриптов

Использовать cookie сессии и заголовок `Origin: https://<DASHBOARD_BASE_URL host>` для мутаций.
Bearer работает только в состоянии «пароль ещё не установлен».

## Защита от двойного нажатия (Idempotency-Key)

Мутирующие эндпоинты пользователей (выдача дней и минут, отзыв, перевыпуск ссылки, смена тарифа,
скидки, кешбэк, VIP, баланс, удаление), а также создание рассылки, гифт-ГБ-ссылки, промокода и
промо-ссылки, фиксы сверки/аудитов и повтор активации принимают заголовок `Idempotency-Key`.
SPA генерирует ключ один раз на отправку формы и повторно использует его при повторе после сетевой
ошибки. Сервер хранит ответ 10 минут (Redis или память процесса) и на повтор с тем же ключом
возвращает сохранённый ответ (`Idempotency-Replayed: true`), не выполняя действие второй раз;
одновременные дубли ждут первый запрос. Тот же ключ с другим телом → 422. Ответы 5xx не
сохраняются (повтор с тем же ключом выполнит действие). Без заголовка поведение прежнее.
Кнопки отправки заблокированы, пока запрос в полёте.

Код: `app/api/dashboard/idempotency.py` (`IdempotentRoute`), `dashboard/src/hooks/useIdempotencyKeys.ts`.
Тесты: `tests/api/test_dashboard_idempotency.py`.
