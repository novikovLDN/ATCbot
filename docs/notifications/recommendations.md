# Рекомендации по автоуведомлениям

[← к оглавлению](README.md) · [← находки](bugs-and-risks.md)

Приоритеты:
- **P0** — чинить сейчас: теряются деньги или ломается основная воронка;
- **P1** — следующая итерация: надёжность и масштаб;
- **P2** — улучшения продукта.

Трудозатраты: **XS** ≤ 2 ч · **S** ≤ 1 дня · **M** 2–3 дня · **L** ≥ неделя.

Порядок укладывается в «Фазу 6. Рассылки и уведомления» из `docs/audit/00_recon.md` §8 и в принцип `docs/audit/SCOPE.md` (без переписывания с нуля, мелкими шагами).

## R-01 · P0 · XS — сбрасывать 7d/1d флаги

Добавить `reminder_7d_sent = FALSE, reminder_1d_sent = FALSE` во все 5 мест сброса: `database/subscriptions.py:1530-1531`, `:1609-1610`, `:1718-1722`, `:1941-1945` (+ в INSERT `:1924-1935`), `:2260-2264` (+ в INSERT `:2240-2251`). Заодно сбрасывать `trial_notif_24h_sent`, `trial_notif_3h_sent` и `trial_notif_bypass_activated_sent` на новой выдаче с `source='trial'`.

**Почему.** Самое дешёвое исправление с максимальным эффектом на продления. Миграция не нужна. Риск: после выкладки пользователи, у которых сейчас TRUE и до конца > 7 дней, получат 7d в текущем периоде — это корректно.

**Тест.** Продление → оба флага FALSE (по образцу `tests/services/test_subscriptions.py`).

## R-02 · P0 · S — `is_reachable` должен возвращаться

1. `UPDATE users SET is_reachable = TRUE WHERE telegram_id = $1 AND is_reachable = FALSE` на **любом** входящем апдейте пользователя. Удобное место — уже существующий `LastSeenMiddleware` (`main.py:170-171`, `app/core/last_seen_middleware.py`), как fire-and-forget.
2. Убрать `COALESCE(u.is_reachable, TRUE) = TRUE` из автопродления (`auto_renewal.py:83`). Финансовая операция не должна зависеть от доставляемости сообщения; отправку уведомления можно пропустить отдельно.
3. Отмечать недоступность только на Forbidden, «chat not found» и «user is deactivated», но не на прочих `TelegramBadRequest` (`app/utils/telegram_safe.py:46-57`).
4. Разово на проде: `SELECT count(*) FROM users WHERE is_reachable = FALSE` — оценить масштаб N-02.

<a id="r-08"></a>
## R-08 · P1 · M — единый журнал уведомлений

Additive-миграция:

```sql
CREATE TABLE notification_log (
  id            BIGSERIAL PRIMARY KEY,
  telegram_id   BIGINT      NOT NULL,
  type          TEXT        NOT NULL,        -- 'paid.7d', 'trial.24h', 'traffic.1gb', 'expired.bypass', …
  period_key    TEXT        NOT NULL,        -- напр. expires_at в ISO, id платежа, id порога трафика + лимит
  status        TEXT        NOT NULL,        -- 'claimed' | 'sent' | 'failed_transient' | 'failed_permanent' | 'skipped'
  attempts      INT         NOT NULL DEFAULT 0,
  claimed_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  sent_at       TIMESTAMPTZ,
  error         TEXT,
  UNIQUE (telegram_id, type, period_key)
);
```

Протокол:
1. `INSERT … ON CONFLICT DO NOTHING RETURNING id` — захват. Нет строки → уже отправлено или отправляется.
2. Отправка.
3. `UPDATE status='sent'` или, при временной ошибке, `failed_transient` + `attempts+1`; ретрай на следующем тике, пока окно открыто.

**Что это даёт.**
- `period_key = expires_at`: продление автоматически даёт новый ключ, **флаги сбрасывать не нужно**. Это закрывает N-01 и все будущие «забыли сбросить».
- Не зависит от ветки `grant_access`.
- Дубли при рестарте невозможны (N-18).
- Готовая база для метрик (R-19).

Булевы флаги в `subscriptions` оставить на время перехода и писать в обе стороны (Compatibility > Cleanliness).

<a id="r-09"></a>
## R-09 · P1 · S–M — доставка и ретраи

- `safe_send_message` (`app/utils/telegram_safe.py:27-70`) должен возвращать тип результата: `sent | permanent (Forbidden, chat not found, deactivated) | transient (RetryAfter, network, 5xx)`, а не `None` на всё подряд.
- Флаг или `status='sent'` ставить только при `sent`. При `permanent` — `skipped` + `is_reachable=FALSE`. При `transient` — ничего, повтор на следующем тике (или `retry_async` по правилу из корневого `CLAUDE.md`, один слой).
- Затронутые места: `trial_notifications.py:208-210, 305-308, 474-480, 520-523`, `app/workers/traffic_monitor.py:63-65, 101-104`, `auto_renewal.py:432-434`. Там ретрая нет вообще: уведомление теряется, если его не отправить в момент продления.

<a id="r-10"></a>
## R-10 · P1 · M — глобальный rate-limit

Сейчас у каждого воркера свой `asyncio.sleep(0.05)` (≈20/с на воркер, `reminders.py:289`, `trial_notifications.py:211`, `auto_renewal.py:435`), у traffic_monitor и фермы паузы нет, у рассылок семафор. Совпадение тиков (рассылка + reminders + trial) даёт больше 30 сообщений/с, а Telegram отвечает 429. Нужен один token-bucket (≤25–30/с глобально, ≤1/с на чат) внутри `safe_send_message`, с учётом `retry_after` и без удержания семафора во сне (см. `00_recon.md` §5).

<a id="r-11"></a>
## R-11 · P1 · S–M — трафик

- Выбирать **самый низкий** пересечённый порог и отмечать его и все выше одним UPDATE (`app/workers/traffic_monitor.py:51-66`). Одно сообщение вместо каскада.
- Отправка через `safe_send_message` и с флагом только при успехе (R-09).
- В `get_active_remnawave_users` (`database/traffic.py:381-402`) добавить `is_reachable`.
- Чтение трафика пакетом (если панель 3.4.x даёт bulk-эндпоинт) или по кольцу из N пользователей за тик вместо GET на каждого раз в 5 мин (`:113-119`). Сейчас 10 тыс. пользователей × 0,2 с ≈ 33 мин на проход.

<a id="r-12"></a>
## R-12 · P1 · S — окна и частота

Перейти от симметричных окон к «догонянию»: слать X, если `now >= expires_at − offset_X`, флаг или запись в журнале по X не стоит, `expires_at > now` и ещё не наступил следующий, более поздний порог. Тогда пропущенный тик не теряет уведомление, а устаревшие не отправляются. Параллельно поднять частоту reminders до 10–15 мин (`reminders.py:384`): запрос дешёвый, дедупликация по флагам. Таймаут 120 с заменить батчами по N с продолжением, как в trial_notifications (`trial_notifications.py:613-633`).

<a id="r-13"></a>
## R-13 · P1 · M — недостающие сценарии

1. **Истечение без обхода.** В `fast_expiry_cleanup.py:308-316` после `status='expired'` — i18n-сообщение «Подписка закончилась» + «Продлить». Отправлять после коммита (R-15).
2. **Не хватило баланса.** В `auto_renewal.py:361-362`: сообщение «На балансе X ₽, нужно Y ₽ — пополните до DD.MM HH:MM» (один раз за период, через `notification_log`). И не записывать `last_auto_renewal_at` в этой ветке (или откатывать его), чтобы после пополнения следующий тик продлил.
3. **Win-back.** Через 3 дня после истечения (и, возможно, через 14) — оффер. Сегмент: истёкшие без активной подписки, `is_reachable`, без повторной покупки. Дедупликация через `notification_log` с `period_key = expires_at`.

<a id="r-14"></a>
## R-14 · P1 · M — источник истины для истечения

Напоминания считаются от `subscriptions.expires_at` (БД), а доступ режет панель по своему `expireAt`. Если синхронизация продления с панелью упала (`auto_renewal.py:386-394` — только лог), пользователь без VPN при «активной» подписке в БД и без напоминаний. Предложение: БД — источник истины, плюс ночная сверка `expireAt` панели (в рамках Фазы 3, Remnawave-клиент) с алертом админу. В перспективе расхождение становится задачей в `provisioning_jobs`.

<a id="r-15"></a>
## R-15 · P1 · S–M — отправка после коммита

`fast_expiry_cleanup.py:244-307`: внутри транзакции только собирать список «кому отправить», отправлять после выхода из `conn.transaction()` и освобождения соединения. `trial_notifications.py:652-799`: разбить на «чтение и решение» → «HTTP Remnawave без соединения» → «короткая транзакция» → «отправка». Это же требование — «не держать соединение во время HTTP» — есть в корневом `CLAUDE.md`.

<a id="r-20"></a>
## R-20 · P2 · L — один «lifecycle notifier»

Сейчас три воркера принимают связанные решения по одним и тем же строкам: reminders (45 мин), trial_notifications (5 мин), fast_expiry_cleanup (1 мин, отправляет сам). Из этого растут N-05 (гонка), N-10 (частота) и N-11 (отправка в транзакции).

Целевая схема:
- fast_expiry только меняет состояние и пишет событие;
- один notifier раз в 1–5 мин одним запросом выбирает кандидатов по всем типам (`trial.*`, `paid.*`, `expired.*`, `winback.*`), дедуплицирует через `notification_log` и шлёт через общий rate-limited sender.

Делать после R-08, R-09, R-12, инкрементально (сначала перенести трафик и истечение, потом напоминания).

<a id="r-21"></a>
## R-21 · P2 · S — автопродление вместо «продлите»

Для таких пользователей вместо «продлите» — «через 7 дней спишем N ₽ с баланса» или «спишем по СБП». Если баланса не хватает — «пополните до …». Это же закрывает часть R-13.
