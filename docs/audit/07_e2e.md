## 1. Как устроено

**Настоящее:**

- база: чистая схема на каждую сессию (`DROP SCHEMA public` → `database.init_db()` = все миграции + inline DDL, как `main.py`);
- aiogram-диспетчер с той же цепочкой middleware, что в `main.main()`; апдейты идут HTTP-запросом в `/telegram/webhook` с секретом;
- FastAPI-роуты вебхуков провайдеров (`/webhooks/platega|wata|cryptobot`) и API дашборда (`/dashboard/api/*`) через `httpx.ASGITransport`;
- `confirmation`, `finalize_purchase`, `grant_access`, `purchase_flow`, `remnawave_*`, outbox `provisioning` и воркер, `auto_renewal`, `reminders`, `trial_notifications`, `fast_expiry_cleanup`, `main.start_db_services` / `retry_db_init`.

**Подделано** (`tests/fakes/`):

| Фейк | Что делает |
|---|---|
| `telegram.FakeTelegram` | aiogram-сессия: каждый вызов Bot API записывается и получает корректный ответ (Message, привязанный к боту). Отсюда тест читает «экран» пользователя и чат админа |
| `remnawave_http.FakeRemnawaveHTTP` | REST Remnawave 3.4.3 как `httpx.MockTransport` **под** `remnawave_api`: POST/PATCH/GET `/api/users`, `/resolve`, `/stream`, squads, hwid, revoke. Весь HTTP-клиент бота настоящий, legacy и outbox идут одним путём. Сбои: `down`, `fail(method, pred, status)`, `ignore_patches` |
| `providers_http.FakeProviders` | API провайдеров для создания счёта (Platega `/transaction/process`, WATA `/links`, CryptoBot `/createInvoice`) + **правильно подписанные** вебхуки: Platega `X-MerchantId/X-Secret`, WATA RSA-SHA512 (тестовый ключ через `WATA_PUBLIC_KEY_PEM`), CryptoBot HMAC-SHA256 |

Время сжато (`asyncio.sleep` → 0), фоновые задачи дожидаются через `World.settle()`. Legacy re-sync держится на «воротах» до `World.release_resync()`.

## 2. Запуск

Без `E2E_DATABASE_URL` все тесты `tests/e2e` пропускаются, герметичный набор остаётся герметичным.

```bash
# локально: любой одноразовый Postgres 16 (схема будет удалена!)
E2E_DATABASE_URL=postgresql://user:pass@localhost:5432/atc_e2e pytest tests/e2e -q
```

Без Docker подойдёт `pgserver` (`pip install pgserver`): `pgserver.get_server(dir).get_uri("atc_e2e")`.

- **CI:** джоба Migration Integrity, шаг «End-to-end scenarios on Postgres» после `tests/db` (тот же `postgres:16`).
- Процесс тестов принудительно в `TZ=UTC`, база — `timezone=UTC`, как на Railway (см. E2E-TZ).
- Время прогона: ~47 с на весь `tests/e2e`. Из них случайные инварианты (200 операций × 2 флага) — ~7 с.
- Повторить случайный прогон с другим seed: `E2E_SEED=<число> E2E_OPS=<число> pytest tests/e2e/test_zz_money_invariants.py`. При падении seed и последние операции будут в сообщении. `E2E_PROFILE=1` печатает время по типам операций.

### Наблюдения

- **Матрица vs e2e.** `T0-TG-NEW-20` и `T0-BAL-NEW-20` (basic/plus, новый юзер, флаг off) **не воспроизводятся** на реальном стеке: выдаётся ровно 10 ГБ. Скорее всего, это артефакт фейка матрицы. Ячейки e2e проходят без xfail.
- **E2E-TZ.** В схеме 78 колонок `TIMESTAMPTZ`, хотя CLAUDE.md говорит «без TZ». Код пишет наивный UTC (`_to_db_utc`), asyncpg трактует наивное значение как **локальное время процесса**. Всё корректно только при `TZ=UTC` процесса (Railway, CI). На машине с МСК все даты сдвигаются на −3 ч (поймано локальным прогоном). Прод не затронут; стоит поправить CLAUDE.md и/или передавать aware-даты в timestamptz.
- **Inline DDL.** На чистой БД `UPDATE users SET referrer_id = referred_by` в `database/core.py` падает. `try/except pass` при этом глотает и два следующих `CREATE INDEX` (`idx_users_referral_code`, `idx_users_referrer_id`). Проверить, создаются ли они миграциями.
- **Пополнение через провайдера** пишет строку `payments` без `purchase_id` (`database/subscriptions.py`, ветка balance top-up в `finalize_purchase`). Выручка считается по `pending_purchases`, поэтому деньги не теряются, но строку оплаты нельзя связать с покупкой. Инвариант-тест проверяет такие пополнения по движению баланса. Низкая, для аудита.
- **Промокод в боте.** После неверного кода единственный выход — кнопка «назад» (`promo_back`). Кнопки тарифов из старых сообщений отвечают «кнопка устарела». Это не баг, но тест проходит этот путь явно.
