# ТЗ: баг «неизвестный тип контента» в агрегаторе подписок

**Для агента на другом боте.** У вас почти наверняка та же проблема, если
агрегатор форвардит User-Agent клиента панели. Документ самодостаточный:
симптом → корневая причина → как диагностировать → фикс → проверка.

---

## 1. Симптом

Пользователь добавляет ссылку агрегатора в VPN-клиент (Happ / Incy /
v2rayTun / v2rayNG) — и клиент пишет **«неизвестный тип контента»** /
«unknown content type». Серверы не появляются.

Характерно:
- **v2rayTun обычно работает**, а **Happ / Incy — нет** (или наоборот, но
  расхождение по клиентам есть).
- На iOS и Android одинаково для одного и того же клиента.
- Прямая ссылка панели (без агрегатора) в том же клиенте работает.

---

## 2. Корневая причина

**Панель Remnawave (и большинство подобных) отдаёт РАЗНЫЙ формат подписки
в зависимости от `User-Agent` запроса** (UA-based subscription templates):

| User-Agent запроса | Что отдаёт панель | Content-Type |
|---|---|---|
| `Happ/...`, `Incy/...` | Клиент-специфичный **JSON** | `application/json` |
| `v2rayTun/...`, `clash`, generic | Стандартный **base64-список** `vless://…` | `text/plain` |

Агрегатор, скачивая upstream-подписку, **форвардит User-Agent КЛИЕНТА**
панели. Поэтому:
- Клиент Happ фетчит агрегатор → агрегатор фетчит панель с UA «Happ» →
  панель отдаёт **JSON** → парсер агрегатора (ждёт base64/vless) не
  распознаёт → мусор → агрегатор отдаёт клиенту `application/json` + мусор →
  **«неизвестный тип контента»**.
- Клиент v2rayTun → панель отдаёт base64 → всё работает.

**Итог:** формат ответа агрегатора зависит от того, какой клиент его
дёргает, потому что UA прозрачно проксируется в панель.

---

## 3. Как диагностировать (доказать)

Дёрните ОДНУ И ТУ ЖЕ upstream sub-ссылку панели двумя UA и сравните:

```bash
# UA Happ → скорее всего JSON
curl -sS -H 'User-Agent: Happ/2.0 (iPhone)' 'https://<panel-sub-host>/<shortuuid>' | head -c 120
# → {"...   (JSON)  ИЛИ  application/json в заголовках

# UA v2rayTun → base64
curl -sS -H 'User-Agent: v2rayTun/2.0' 'https://<panel-sub-host>/<shortuuid>' | head -c 120
# → dmxlc3M6Ly8...  (base64, декодится в vless://)
```

Если тела разные — диагноз подтверждён. Ключевые сигналы:
- Content-Type `application/json` vs `text/plain`.
- Тело начинается с `{` / `[` (JSON) vs base64-алфавит.
- Число распарсенных серверов: 1 (мусор из JSON) vs N (реальные).

---

## 4. Фикс

Агрегатор должен скачивать панель с **ФИКСИРОВАННЫМ User-Agent**, который
заставляет панель отдавать **универсальный base64-список vless**, а НЕ с
UA клиента. И всегда отдавать клиенту `Content-Type: text/plain`.

```python
# Константа (override через ENV/config при желании).
UPSTREAM_UA = "v2rayTun/2.0 (sub-aggregator)"   # проверенно даёт base64

# При скачивании каждой upstream-подписки:
resp = await client.get(upstream_url, headers={"User-Agent": UPSTREAM_UA})
#                                                            ^^^^^^^^^^^ НЕ UA клиента!

# На выход клиенту — ВСЕГДА text/plain, НЕ пробрасывать панельный content-type:
return Response(
    content=merged_base64_bytes,
    media_type="text/plain; charset=utf-8",   # не application/json!
    headers={... subscription-userinfo, profile-*, x-cache ...},
)
```

Почему это правильно:
- **base64-список `vless://…` — универсальный формат**. Его импортируют ВСЕ
  клиенты (Happ, Incy, v2rayTun, v2rayNG) на iOS и Android. JSON — это
  клиент-специфичная оптимизация, но base64 Happ тоже отлично ест.
- Фикс-UA убирает зависимость выдачи от того, кто дёрнул агрегатор.
- `text/plain` — то, что клиент ждёт от base64-подписки.

⚠️ НЕ пробрасывайте content-type панели вслепую: панельный
`application/json` (для Happ-UA) — как раз и ломает клиента.

---

## 5. Смежные грабли (проверьте заодно)

При работе агрегатора со старой БД всплывают ещё две беды с upstream-URL —
если у вас live-резолв из subscriptions/bypass, часть может не касаться, но
проверьте:

1. **Устаревший путь `/api/sub/<id>`.** Панель могла обновиться и отдавать
   подписку на `/<shortuuid>` без префикса `/api/sub/`. Старый путь → HTTP
   502. Нормализуйте: `url.replace("/api/sub/", "/")`.
2. **Мёртвый host.** В сохранённых URL бывает снесённый фронт-домен
   (у нас — `subscription.vps-cloud.uk`). Принудительно бейте в живой
   sub-host панели, что бы ни лежало в БД.

Обе — тоже приводят к пустой склейке → 503 → «неизвестный тип контента».

---

## 6. Диагностический инструмент (рекомендуется)

Сделайте команду-чекер (у нас `/aggcheck [tg_id]`), которая для юзера:
1. Резолвит его пару / upstream-ссылки.
2. Качает обе панель-ссылки **фикс-UA**, показывает: HTTP-код, content-type,
   **первые символы тела** (сразу видно JSON vs base64), число серверов.
3. Дёргает публичный URL агрегатора несколькими UA (iOS Happ / Android Happ
   / v2rayTun) и показывает content-type + серверов для каждого.

Это мгновенно вскрывает: UA-формат, мёртвый URL, домен/nginx или клиентский
кеш. Именно так мы нашли причину за один прогон.

---

## 7. Проверка после фикса

1. Чекер: обе upstream-ссылки → `text/plain`, тело `base64/…`, N серверов
   (не JSON / 1).
2. Публичный URL на ВСЕ UA (iOS/Android/v2rayTun) → одинаково `text/plain`,
   N серверов.
3. Реальный тест: добавить подписку в **Happ на Android** → импортируется со
   всеми серверами.
4. Только после этого раскатывать на всех.

---

## 8. Резюме одной фразой

**Не форвардьте UA клиента панели — качайте фикс-UA, который даёт base64, и
всегда отдавайте text/plain.** Это устраняет «неизвестный тип контента» на
всех клиентах и платформах.
